# Quorum — Production Readiness Audit Plan

**Tier:** `tier3_verification` · **Status:** ready to execute, not yet run · **Author's note:** written after Sessions 1–9 of `QUORUM_FINAL_COMPLETION_PLAN.md` (`DEC-165`–`DEC-177`), at Preethish's own explicit request for a "production grade, rigorous plan to check what's done perfectly and what's still left."

## 0. Why this document exists, and why it's a separate document

`STATUS_INDEX.md` already tracks "is this real and tested" (32 open items, most resolved) and a "Product Reality" section tracking "what can a user see and do." `DECISIONS_LOG.md` already records why every decision was made. Neither is an **audit instrument** — a thing you actually execute, checklist in hand, to independently re-confirm a claim rather than read a paragraph asserting it.

That distinction matters *specifically on this project*, not generically. Tonight alone, three independent fresh-context/CRITICAL-tier reviews caught this session's own log entries overstating things: a test count (claimed 11, actually 5), a suite total quietly computed instead of re-run (turned out wrong once actually re-run — 880/17, not 892/5), and a tier self-classification that skipped a whole trigger condition (a new secret type, requiring the CRITICAL-tier review Rule 6 actually calls for). Every one of those mistakes was made in good faith, by the same discipline that's supposed to prevent exactly this, and every one was still wrong until independently re-checked. **The entire premise of this audit plan is that the log's own claims are the thing being tested, not the source of truth being consulted.** Every checklist item below says "run this and look" or "read this file directly," never "confirm `DECISIONS_LOG.md` says X."

This document does not replace `QUORUM_FINAL_COMPLETION_PLAN.md` (still the roadmap for what's *left to build*) or `STATUS_INDEX.md` (still the living index of *current state*). It is the missing third piece: a rigorous, independent, re-runnable check on whether everything those two documents claim is done is *actually, verifiably* done — and a precise, non-overlapping accounting of what genuinely is not.

## 1. What "production-ready" means here — the actual bar, not a vibe

Per the final completion plan's own binding Decision 2, confirmed directly with Preethish: production-ready means **fully verified end-to-end, plus a real Google Play Store presence** (Closed Testing is sufficient — see §11.6). It explicitly does **not** require a monitoring/alerting stack or additional legal documents beyond what Play Console's own Data Safety form demands. Keep that scope honest in both directions while running this audit: don't treat a missing Prometheus dashboard as a blocker, and don't wave through a genuinely broken S3 backstop because "it's just a portfolio project."

Two axes matter, and this plan checks both separately because this project's own history (`DEC-120`–`128`, the whole-system-checkpoint incident) proved they can silently diverge for months:

- **Is the code real, tested, and correct?** (`STATUS_INDEX.md`'s own long-standing question.)
- **Can a real, signed-in user currently see or do the thing?** (the "Product Reality" section's question — code that's real and correct but has zero real callers, like `POST /quick_capture/extracted` or the FCM send path today, is *not* production-ready by this project's own definition, even though nothing about it is broken.)

## 2. Ground rules for whoever runs this audit (a future session, or Preethish directly)

1. **Never accept a DEC-log paragraph as evidence.** If an entry says "891 passed, 5 failed," re-run the suite and get a fresh number. If an entry says "the S3 backstop cannot be bypassed," read `action_executor.py` and `persist_gate_verdict()` yourself and trace the actual guard condition.
2. **Every external-service test failure needs its *specific* cause named, not assumed.** This project has exactly two recurring, well-understood external failure classes right now — the shared 20/day Gemini quota, and the expired sandbox Google OAuth refresh token. A failure that doesn't match either of those patterns by name is a **real, new finding**, not noise to wave away with "probably the usual thing."
3. **A stakes/security claim gets read at the code level, never taken on the strength of a comment.** Comments in this codebase are unusually good, but a comment describing a guard is not the guard. `gate/orchestration.py`, `router.py`'s `STAKES_TABLE`, and `action_executor.py`'s S3 backstop are the three files where this rule is non-negotiable.
4. **"Zero real callers" is itself a valid, complete audit finding** — not a bug to silently fix mid-audit. If this plan finds dead code, record it precisely (what file, what would call it, what's blocking that) and move on; don't start building the missing caller as an unplanned detour from the audit itself.
5. **Record what you could NOT verify, distinctly from what you verified and found correct.** The two genuinely different external blockers in this project (Gemini quota exhaustion, expired sandbox OAuth) will make some checks below un-runnable on any given day. "Blocked, retry after quota reset" is an honest, acceptable audit outcome; silently skipping the check and marking it ✅ anyway is not.

## 12. Risk register — real, live risks worth naming explicitly, not buried in a paragraph

- **The shared, hard 20-request/day Gemini quota is a real, permanent production capacity constraint, not just a testing inconvenience.** Every one of the Judge (Stage B, every S2/S3 action), Quick-capture's extraction call, and `downstream_translation`'s negotiation-option translation draws on this *same* quota, uncoordinated beyond `core/gemini_quota.py`'s own reservation guard. For a single real user in genuine daily use, 20 calls/day is plausibly enough — but this has never been measured against real, sustained personal usage, only against this project's own heavy *testing* load (which has repeatedly exhausted it within a single working session). **Before Session 11's own final verification pass, this plan recommends a real, dedicated measurement: how many Gemini-consuming actions does one real day of intended personal use actually generate**, and whether 20/day is a comfortable margin or a real, live ceiling a genuine user could hit. This has not been done and is not the same question as "did testing exhaust the quota tonight."
- **The `on_device_extraction.dart`/`llamadart` integration has never been exercised on a real device at all** — not "not verified," genuinely never attempted. Its very first real run should be treated as a real, standalone risk (a native FFI plugin, a multi-GB download, a real inference call) worth its own dedicated, unhurried session — not folded into a longer, already-eventful device session as an afterthought, which is exactly how tonight's own Session-2 device work surfaced two genuine, previously-invisible bugs.
- **No RLS (Row-Level Security) policy has ever been confirmed or disclaimed for the real Supabase tables.** Every real per-user query in this backend enforces isolation at the application layer (`WHERE user_id = $1`, confirmed via this project's own extensive cross-user-isolation test suite) — but whether Postgres's own RLS is additionally enabled as a second, independent layer has not been checked or discussed anywhere in this project's real history, as far as this audit plan's own drafting could confirm. Worth a direct, explicit check (`SELECT relrowsecurity FROM pg_class WHERE relname = 'tasks';`, and similarly for every per-user table) and a real, disclosed decision either way, rather than an unexamined gap.
- **A real, single point of failure for every autonomous job: one shared `INTERNAL_DRAIN_SECRET`.** All six `pg_cron` jobs, and any future one, authenticate with the identical shared secret. A leak of this one value (the same plaintext-in-`cron.job.command` gap named above) would let an attacker trigger every internal route, including `DELETE /account`-adjacent paths reachable through them, for every real user in the deployment. This is not a new finding, but it has never been framed explicitly as a single-secret blast-radius risk before, worth carrying into any future rotation-priority decision.

## 13. Running this audit — sequencing and effort
